# ECS Rules

## 1. Purpose

This document defines Amazon Elastic Container Service (ECS) standards for the Agentic SDLC platform.

ECS is responsible for running, maintaining, scaling, and deploying containerized applications generated by the platform.

The platform must use ECS in a secure, reliable, observable, and production-ready manner.

---

## 2. ECS Standards Summary

ECS deployments must follow these principles:

* Infrastructure as Code
* Immutable container images
* Least-privilege IAM
* Private networking where appropriate
* Secure secrets injection
* Health checks
* Controlled deployments
* Auto Scaling
* CloudWatch monitoring
* Automated rollback
* Environment separation
* Deployment traceability
* Production approval gates

---

## 3. Recommended ECS Architecture

For a typical production application:

```text
Internet
   ↓
Route 53
   ↓
Application Load Balancer
   ↓
Target Group
   ↓
ECS Service
   ↓
ECS Tasks
   ↓
Docker Containers
   ↓
ECR
```

Supporting services:

```text
ECS
 ├── CloudWatch
 ├── Secrets Manager
 ├── IAM
 ├── RDS
 ├── ElastiCache / Redis
 └── ECR
```

---

## 4. ECS Launch Type

The platform should prefer:

```text
ECS Fargate
```

when serverless container execution is appropriate.

Fargate removes the need to manage ECS container instances.

Use ECS on EC2 only when specific workload or infrastructure requirements justify it.

---

## 5. ECS Cluster

A cluster should logically group workloads.

Example:

```text
agentic-sdlc-prod
agentic-sdlc-staging
agentic-sdlc-dev
```

Environment separation should follow organizational requirements.

---

## 6. Environment Separation

Production and non-production workloads should be isolated.

Recommended:

```text
Development
     ↓
Staging
     ↓
Production
```

Avoid accidentally deploying development configuration into production.

---

## 7. ECS Service

An ECS Service maintains the desired number of running tasks.

Example:

```text
ECS Service
    ↓
Desired Count = 3
    ↓
Task 1
Task 2
Task 3
```

The service should automatically replace unhealthy or stopped tasks.

---

## 8. Desired Task Count

Production services should have an explicitly configured desired task count.

Example:

```text
Minimum Tasks = 2
Desired Tasks = 2
Maximum Tasks = 10
```

The exact values must depend on application capacity requirements.

---

## 9. High Availability

Production services should normally run multiple tasks.

Example:

```text
ALB
 ↓
ECS Service
 ├── Task A → AZ-1
 ├── Task B → AZ-2
 └── Task C → AZ-3
```

Tasks should be distributed across Availability Zones where supported and practical.

---

## 10. ECS Task Definition

The task definition defines how containers run.

It should specify:

* Container image
* CPU
* Memory
* Port mappings
* Environment variables
* Secrets
* Logging
* Health checks
* IAM roles
* Storage
* Runtime configuration

---

## 11. Task Definition Versioning

Task definitions are versioned.

Example:

```text
myapp:42
myapp:43
myapp:44
```

Every deployment should create a traceable task definition revision.

---

## 12. Container Image

The task definition must reference an approved ECR image.

Example:

```text
123456789012.dkr.ecr.ap-south-1.amazonaws.com/myapp:152
```

Prefer an immutable image digest for production deployments where practical.

---

## 13. Never Deploy `latest`

Production ECS services must not depend exclusively on:

```text
myapp:latest
```

Use:

```text
myapp:152
```

or:

```text
myapp@sha256:abc123...
```

This ensures deployment reproducibility.

---

## 14. ECS and ECR Flow

```text
Git
 ↓
Jenkins
 ↓
Docker Build
 ↓
Security Scan
 ↓
ECR
 ↓
Image Digest
 ↓
ECS Task Definition
 ↓
ECS Service
```

The exact validated image should be deployed.

---

## 15. CPU Configuration

Each task must have an appropriate CPU allocation.

Example:

```text
CPU = 512
```

The value must be selected based on application requirements and load testing.

Avoid arbitrarily assigning large CPU values.

---

## 16. Memory Configuration

Memory must be explicitly configured.

Example:

```text
Memory = 1024 MB
```

Memory allocation should be based on actual application behavior.

Insufficient memory can cause:

```text
OOMKilled
```

and task restarts.

---

## 17. CPU and Memory Testing

Before production:

```text
Normal Load
   ↓
CPU/Memory Monitoring
   ↓
Peak Load
   ↓
Capacity Validation
```

Use CloudWatch metrics to determine appropriate resource values.

---

## 18. Port Mapping

Only required ports should be exposed.

Example:

```text
Container Port = 8000
Protocol = TCP
```

For FastAPI:

```text
ALB
 ↓
Container:8000
```

Do not expose unnecessary administrative ports.

---

## 19. Network Mode

Fargate tasks should normally use:

```text
awsvpc
```

This provides each task with its own network interface.

---

## 20. VPC

ECS workloads should run inside an appropriate VPC.

Example:

```text
VPC
 ├── Public Subnets
 │     └── ALB
 │
 └── Private Subnets
       └── ECS Tasks
```

Production application tasks should normally run in private subnets.

---

## 21. Public IP

Production ECS application tasks should normally not receive public IP addresses.

Preferred:

```text
Assign Public IP = DISABLED
```

Traffic should flow through controlled network components.

---

## 22. Internet Access

Private ECS tasks may require outbound internet access for:

* External APIs
* Package repositories
* AWS services

When internet access is required:

```text
Private ECS Subnet
       ↓
NAT Gateway
       ↓
Internet
```

Use VPC endpoints for supported AWS services when appropriate.

---

## 23. Security Groups

ECS task security groups must allow only required traffic.

Example:

```text
ALB Security Group
       ↓
ECS Security Group
       ↓
Port 8000
```

Do not allow unrestricted inbound access such as:

```text
0.0.0.0/0 → ECS:8000
```

unless explicitly required and approved.

---

## 24. Security Group Separation

Prefer separate security groups for:

```text
ALB
ECS
RDS
Redis
```

Example:

```text
Internet
   ↓
ALB SG
   ↓
ECS SG
   ↓
RDS SG
```

Each layer should trust only the required upstream layer.

---

## 25. IAM Roles

ECS commonly uses two important roles:

```text
Task Execution Role
Task Role
```

These roles have different responsibilities.

---

## 26. Task Execution Role

The execution role is used by ECS infrastructure to perform actions such as:

* Pulling ECR images
* Sending logs to CloudWatch
* Retrieving configured secrets

It should not contain unnecessary application permissions.

---

## 27. Task Role

The task role provides AWS permissions to the running application.

Example:

```text
FastAPI Container
      ↓
Task Role
      ↓
S3 / DynamoDB / SQS / Secrets Manager
```

Only required application permissions should be granted.

---

## 28. Never Use Static AWS Credentials

Applications running on ECS must not contain:

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

as hardcoded credentials.

Use the ECS task role instead.

---

## 29. Secrets Management

Production secrets should be stored in:

```text
AWS Secrets Manager
```

or another approved centralized secret-management system.

Do not store secrets inside:

```text
Dockerfile
Git
ECR image
Task definition plaintext
Jenkinsfile
Application source
```

---

## 30. Secret Injection

Preferred:

```text
AWS Secrets Manager
       ↓
ECS Task Definition
       ↓
Container
       ↓
Application
```

Only the required secret should be exposed to the application.

---

## 31. Environment Variables

Environment variables may contain non-sensitive configuration.

Example:

```text
ENVIRONMENT=production
LOG_LEVEL=INFO
PORT=8000
```

Sensitive values must use secret injection.

---

## 32. Logging

Containers should write application logs to:

```text
stdout
stderr
```

ECS should forward logs to CloudWatch Logs.

Example:

```text
Container
   ↓
awslogs
   ↓
CloudWatch Logs
```

---

## 33. Log Group

Use predictable log group names.

Example:

```text
/ecs/myapp/production
/ecs/myapp/staging
/ecs/myapp/development
```

Log retention should be explicitly configured.

---

## 34. Structured Logging

Production applications should preferably produce structured logs.

Example:

```json
{
  "level": "INFO",
  "request_id": "abc123",
  "service": "backend",
  "message": "Request completed"
}
```

Secrets and sensitive information must not be logged.

---

## 35. Health Checks

Containers should define appropriate health checks.

For FastAPI:

```text
GET /health
```

may be used for liveness.

Example:

```dockerfile
HEALTHCHECK CMD curl --fail http://localhost:8000/health || exit 1
```

Only install `curl` when required by the chosen health-check implementation.

---

## 36. Readiness

Applications should expose a readiness endpoint where appropriate.

Example:

```text
GET /readiness
```

Readiness should verify that required dependencies are available before accepting traffic.

---

## 37. ALB Health Check

The target group's health check should use an appropriate endpoint.

Example:

```text
Path: /health
Port: traffic-port
Protocol: HTTP
```

The endpoint must respond quickly and reliably.

---

## 38. Health Check Failure

When a task fails its health check:

```text
Unhealthy Task
      ↓
Removed from Traffic
      ↓
Task Replaced
      ↓
New Task Starts
      ↓
Health Check
      ↓
Healthy
```

---

## 39. Graceful Shutdown

Applications must handle termination signals correctly.

The application should:

* Stop accepting new work
* Complete safe in-flight work
* Close connections
* Flush logs
* Release resources
* Exit cleanly

This is especially important during ECS deployments and scaling.

---

## 40. Deployment Strategy

Production deployments should use controlled ECS deployment strategies.

Typical:

```text
Rolling Deployment
```

or:

```text
Blue/Green Deployment
```

depending on reliability requirements.

---

## 41. Rolling Deployment

Example:

```text
Old:
Task 1
Task 2
Task 3

        ↓ Deployment

New:
Task 1
Task 2
Task 3
```

ECS gradually replaces old tasks while maintaining service availability.

---

## 42. Deployment Configuration

Deployment configuration should control:

```text
Minimum Healthy Percent
Maximum Percent
Deployment Circuit Breaker
Rollback
```

Values should be selected based on workload requirements.

---

## 43. Deployment Circuit Breaker

Production services should use an ECS deployment circuit breaker where appropriate.

Conceptually:

```text
Deployment
    ↓
Tasks fail
    ↓
Deployment Circuit Breaker
    ↓
Deployment stops
    ↓
Rollback
```

This prevents a failed deployment from continuously replacing healthy tasks.

---

## 44. Automatic Rollback

Production deployments should support automatic rollback when the deployment fails.

Rollback may occur because:

* Tasks fail to start
* Health checks fail
* Application crashes
* Target group becomes unhealthy
* Deployment circuit breaker triggers

---

## 45. Rollback Image

Rollback should use a previously validated immutable image.

Example:

```text
Current:
myapp@sha256:NEW

Rollback:
myapp@sha256:PREVIOUS
```

Do not rebuild the application during an incident unless required.

---

## 46. ECS Auto Scaling

Production services should use ECS Service Auto Scaling where workload variability requires it.

Architecture:

```text
ALB
 ↓
ECS Service
 ↓
Tasks
 ↓
Auto Scaling
```

---

## 47. Auto Scaling Minimum

Define the minimum number of tasks.

Example:

```text
Min Capacity = 2
```

This helps maintain availability.

---

## 48. Auto Scaling Maximum

Define a maximum task count.

Example:

```text
Max Capacity = 10
```

This protects against uncontrolled scaling and unexpected cost.

---

## 49. Desired Capacity

The desired count should represent the normal operating capacity.

Example:

```text
Minimum = 2
Desired = 2
Maximum = 10
```

---

## 50. CPU-Based Scaling

A service may scale based on CPU utilization.

Example:

```text
CPU Target = 60%
```

Conceptual flow:

```text
CPU > Target
   ↓
Scale Out

CPU < Target
   ↓
Scale In
```

---

## 51. Memory-Based Scaling

Memory utilization may also be used.

Example:

```text
Memory Target = 70%
```

The scaling strategy should match actual workload behavior.

---

## 52. Request-Based Scaling

For ALB-backed services, request count per target may be used when appropriate.

Example:

```text
Requests per Target
        ↓
Scaling Policy
        ↓
ECS Tasks
```

This may be more representative than CPU for some applications.

---

## 53. Scaling Cooldowns

Scale-out and scale-in behavior should avoid excessive oscillation.

Use appropriate:

* Cooldown periods
* Evaluation periods
* Target values
* Step scaling thresholds

---

## 54. Background Agent Jobs

Long-running Agentic SDLC jobs should not depend on a normal synchronous HTTP request.

Preferred:

```text
API
 ↓
Queue / Job System
 ↓
Worker
 ↓
Agent Workflow
 ↓
Job Status
```

The API can return:

```json
{
  "job_id": "job-123",
  "status": "queued"
}
```

---

## 55. Agent Worker Services

If the platform uses dedicated workers:

```text
ECS Service
   ↓
Agent Worker Tasks
```

Workers may be scaled independently from the API service.

Example:

```text
API Service
Min=2 Max=10

Worker Service
Min=1 Max=20
```

---

## 56. ECS and RAG

If the Agentic SDLC platform uses RAG:

```text
API
 ↓
ECS
 ↓
RAG Service
 ↓
Vector Database
```

Credentials and vector database access must use secure runtime configuration.

---

## 57. ECS and LLM APIs

LLM API keys must never be stored in the container image.

Preferred:

```text
Secrets Manager
      ↓
ECS
      ↓
Environment / Runtime Secret
      ↓
Agent
      ↓
LLM API
```

---

## 58. ECS and MCP

MCP servers may run as independent ECS services when appropriate.

Example:

```text
Agent
 ↓
MCP Server
 ├── GitHub
 ├── Jenkins
 ├── AWS
 └── CloudWatch
```

MCP credentials should remain outside the LLM context and container image.

---

## 59. Service Discovery

Service discovery may be used when ECS services communicate internally without an ALB.

Use it only when required.

For externally exposed applications, an ALB is normally preferred.

---

## 60. Load Balancer

Production HTTP applications should generally use an Application Load Balancer when:

* HTTP/HTTPS traffic is required
* Multiple ECS tasks are used
* Health checks are needed
* Traffic distribution is required

---

## 61. HTTPS

Production external traffic should use HTTPS.

Recommended:

```text
Client
 ↓ HTTPS
ALB
 ↓ HTTP/HTTPS
ECS
```

TLS certificates should be managed through AWS Certificate Manager or an approved certificate system.

---

## 62. HTTP Redirect

If HTTP is exposed externally:

```text
HTTP :80
   ↓
Redirect
   ↓
HTTPS :443
```

Application traffic should use HTTPS.

---

## 63. Route 53

DNS may point to the ALB.

Example:

```text
api.example.com
       ↓
Route 53
       ↓
ALB
       ↓
ECS
```

DNS records should be managed through approved Infrastructure as Code.

---

```text

   ↓
Unit Tests
   ↓
Integration Tests
   ↓
Security Tests
   ↓
Docker Build
   ↓
Image Scan
   ↓
ECR Push
```

Terraform should manage infrastructure such as:

```text
ECS Cluster
ECS Service
Task Definition
ALB
Target Groups
Security Groups
IAM Roles
CloudWatch
Auto Scaling
```

Application image promotion should normally remain a CI/CD responsibility.

---

## 66. Infrastructure vs Application Deployment

Separate:

```text
Infrastructure Deployment
```

from:

```text
Application Image Deployment
```

Example:

```text
Terraform
 ↓
Create ECS Infrastructure

Jenkins
 ↓
Build Image
 ↓
Push ECR
 ↓
Deploy Image
```

This reduces unnecessary infrastructure changes during application releases.

---

## 67. ECS Deployment Idempotency

Repeated deployment commands should produce predictable results.

Example:

```text
Deploy Image A
     ↓
Deploy Image A Again
     ↓
No Unnecessary Infrastructure Change
```

Deployment automation should safely handle retries.

---

## 68. Deployment Timeout

Jenkins should wait for ECS deployment completion with a defined timeout.

Example conceptual flow:

```text
Update ECS
    ↓
Wait
    ↓
Deployment Complete?
    ├── Yes → Continue
    └── No → Timeout / Failure
```

Never wait indefinitely.

---

```bash
curl --fail https://api.example.com/health
```

## 72. ECS Monitoring

Monitor:

* CPU utilization
* Memory utilization
* Running task count
* Desired task count
* Pending tasks
* Deployment failures
* Target health
* HTTP 4xx
* HTTP 5xx

Production services should have appropriate alarms.

Examples:

```text
High CPU
High Memory
High 5xx
Unhealthy Targets
Running Tasks < Desired
Deployment Failure
```

Critical alarms should have an appropriate notification mechanism.

---

## 74. ECS Events

ECS service events should be monitored during deployments.

They can help identify:

* Image pull failures
* IAM errors
* Health-check failures
* Resource shortages
* Networking problems
* Task startup failures

---

## 75. ECS Task Failure

If a task repeatedly fails:

```text
Task Failure
   ↓
Inspect ECS Events
   ↓
Inspect CloudWatch Logs
   ↓
Check Image
   ↓
Check IAM
   ↓
Check Network
   ↓
Check Secrets
   ↓
Check Health Check
```

Do not blindly increase desired task count.

---

## 76. Container Exit Codes

Application failures should be investigated using container exit codes.

Common causes:

```text
Configuration Error
Missing Secret
Application Crash
Dependency Failure
OOM
Incorrect Command
Port Misconfiguration
```

---

## 77. ECS Resource Limits

CPU and memory should be intentionally configured.

Avoid allocating excessive resources without evidence.

Capacity decisions should consider:

```text
Average Load
Peak Load
Latency
Concurrency
Cost
Scaling Behavior
```

---

## 78. Cost Optimization

ECS cost should be controlled using:

* Right-sized tasks
* Auto Scaling
* Appropriate minimum capacity
* Spot capacity where appropriate
* Image optimization
* Log retention
* Resource monitoring

Cost optimization must not compromise required availability or security.

---

## 79. ECS Security

Production ECS workloads must follow:

* Least privilege
* Private networking
* Restricted security groups
* IAM roles
* Secrets Manager
* Encryption
* Image scanning
* No privileged containers
* No unnecessary Linux capabilities
* No hardcoded credentials
* Restricted network access

---

## 80. Privileged Containers

Production containers must not run in privileged mode unless explicitly required and security-approved.

Avoid:

```text
privileged = true
```

---

## 81. Linux Capabilities

Containers should run with the minimum required Linux capabilities.

Unnecessary capabilities should be dropped.

---

## 82. Read-Only Filesystem

For applications that support it, use a read-only root filesystem.

Example concept:

```text
Readonly Root Filesystem = true
```

Temporary writable locations should be explicitly configured.

---

## 83. Docker Socket

Containers must not receive unrestricted access to the host Docker socket.

Avoid:

```text
/var/run/docker.sock
```

unless there is a highly specific, approved use case.

---

## 84. ECS Agent Execution Safety

If the Agentic SDLC platform executes generated code:

```text
Agent
 ↓
Sandbox / Controlled Worker
 ↓
ECS Task
 ↓
Restricted Runtime
```

Do not execute untrusted generated code inside the main production API container.

---

## 90. ECS Agent Safety Rules

The ECS Agent must not:

* Deploy an unapproved image
* Deploy an image with failed mandatory security checks
* Expose ECS tasks publicly without approval
* Add unrestricted security-group access
* Add unnecessary IAM permissions
* Hardcode credentials
* Disable health checks to force deployment success
* Disable security controls
* Delete production services without authorization
* Scale production indefinitely
* Bypass required deployment approval

## 92. ECS Implementation Decision Matrix

| Situation           | Recommended Implementation    | Avoid                    |
| ------------------- | ----------------------------- | ------------------------ |
| Container runtime   | ECS Fargate where appropriate | Unmanaged servers        |
| Production tasks    | Multiple tasks                | Single task              |
| Application subnet  | Private subnet                | Public subnet by default |
| Public access       | ALB                           | Direct task exposure     |
| Image source        | Private ECR                   | Arbitrary registry       |
| Image version       | Immutable tag/digest          | `latest`                 |
| AWS credentials     | ECS task role                 | Static credentials       |
| Secrets             | Secrets Manager               | Environment plaintext    |
| Logs                | CloudWatch                    | Local-only logs          |
| Health              | ALB/container health checks   | No health checks         |
| Deployment          | Rolling/Blue-Green            | Uncontrolled replacement |
| Rollback            | Previous validated image      | Rebuild during incident  |
| Scaling             | ECS Auto Scaling              | Manual-only scaling      |
| IAM                 | Least privilege               | AdministratorAccess      |
| Security group      | Layer-specific access         | `0.0.0.0/0`              |
| Infrastructure      | Terraform                     | Manual production setup  |
| Deployment          | Jenkins/CI                    | Manual-only deployment   |
| Agent execution     | Isolated worker               | Main API container       |
| Production approval | Required gate                 | Uncontrolled auto-deploy |

## 93. ECS Acceptance Criteria

An ECS implementation is accepted only when:

1. ECS cluster is available.
2. Correct environment is selected.

## 94. Production Quality Gate

Production ECS deployment must be blocked when:

```text
Invalid Image
       OR
Security Scan Failed
       OR
Secret Detected
       OR
Invalid IAM
       OR
Invalid Networking
       OR
Unrestricted Security Group
       OR
Task Definition Invalid
       OR
ECS Deployment Failed
       OR
Tasks Unhealthy
       OR
Target Group Unhealthy
       OR
Health Check Failed
       OR
Smoke Test Failed
       OR
Required Approval Missing
```

## 95. Final ECS Rule

The Agentic SDLC platform must treat ECS deployment as a controlled production release, not simply as an API call that starts a container.

The complete flow must be:

```text
Source Code
     ↓
Testing
     ↓
Security Validation
     ↓
Docker Build
     ↓
ECR
     ↓
Immutable Image
     ↓
ECS Task Definition
     ↓
ECS Service
     ↓
ALB
     ↓
Health Checks
     ↓
Auto Scaling
     ↓
CloudWatch
     ↓
Smoke Test
     ↓
Production
```

**Final Rule:**

> Every production application generated by the Agentic SDLC platform must be deployed to ECS using an approved immutable image, least-privilege IAM, secure networking, runtime secret management, health checks, controlled deployment and rollback mechanisms, appropriate Auto Scaling, CloudWatch monitoring, and mandatory production quality gates.
