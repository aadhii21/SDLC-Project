# Frontend Testing Standards

## 1. Purpose

This document defines the testing standards for all frontend applications generated by the Agentic SDLC platform.

The Testing Agent must use these standards when generating, reviewing, executing, and validating frontend tests.

The frontend testing strategy must verify:

* Component behavior
* UI functionality
* API integration
* User workflows
* Authentication
* Authorization
* Form validation
* Loading states
* Error states
* Empty states
* Responsive behavior
* Accessibility
* Figma design compliance
* Browser compatibility
* Security
* Performance

---

# 2. Testing Principles

Frontend tests must follow these principles:

1. Test user behavior instead of implementation details.
2. Test business-critical functionality first.
3. Prefer deterministic tests.
4. Avoid unnecessary mocking.
5. Keep tests independent.
6. Tests must be repeatable.
7. Tests must run automatically in CI/CD.
8. Do not depend on production services during automated tests.
9. Do not expose secrets in test code.
10. Every critical user workflow must have automated coverage.

---

# 3. Testing Pyramid

Frontend testing should follow this approximate structure:

```text
             E2E Tests
                ↑
        Integration Tests
                ↑
       Component Tests
                ↑
          Unit Tests
```

Recommended distribution:

| Test Type         | Recommended Coverage |
| ----------------- | -------------------: |
| Unit Tests        |                 High |
| Component Tests   |                 High |
| Integration Tests |               Medium |
| E2E Tests         |   Critical workflows |
| Visual Tests      | Important UI screens |

Do not attempt to cover every UI interaction through E2E tests.

# 4. Testing Strategy

The frontend Testing Agent must generate tests at multiple levels.

```text
Component
    ↓
Component Tests
    ↓
API Integration
    ↓
Integration Tests
    ↓
User Workflow
    ↓

```

Example:

```text

    ↓
Validate email/password
    ↓
Call authentication API
    ↓
Store authentication state
    ↓
Redirect user
    ↓

```

Tests should validate the complete flow where appropriate.

# 6. Unit Testing

Unit tests must validate isolated functions and utilities.

Examples:

* Utility functions
* Data transformation
* Validation functions
* Formatting functions
* Custom hooks where appropriate
* Business logic

Example:

```typescript
describe("formatCurrency", () => {
  it("formats currency correctly", () => {
    expect(formatCurrency(1000)).toBe("$1,000.00");
  });
});
```

Unit tests should not depend on:

* Real APIs
* Real databases
* External services
* Production credentials

---

# 7. Component Testing

Component tests must validate component behavior from the user's perspective.

Test:

* Rendering
* User interaction
* Props
* Events
* Conditional rendering
* Loading state
* Error state
* Empty state
* Disabled state
* Accessibility behavior

Example:

```typescript
it("submits the login form", async () => {
  render(<LoginForm />);

  await user.type(
    screen.getByLabelText("Email"),
    "user@example.com"
  );

  await user.type(
    screen.getByLabelText("Password"),
    "password"
  );

  await user.click(
    screen.getByRole("button", { name: "Login" })
  );

  expect(mockLogin).toHaveBeenCalled();
});
```

---

# 8. Integration Testing

Integration tests must verify interactions between multiple frontend components or services.

Examples:

```text
Page
 ↓
Component
 ↓
API Client
 ↓
State Management
 ↓
UI Update
```

Integration tests should verify that these components work together correctly.

Example:

```text
Project Page
    ↓
Fetch Projects API
    ↓
Update State
    ↓
Render Project List
```

---

# 9. API Mocking

Automated frontend tests must not depend on live backend services.

Use API mocking for:

* Success responses
* Validation errors
* Authentication errors
* Authorization errors
* Server errors
* Network failures
* Timeout scenarios

Example:

```text
GET /api/v1/projects

Mock response:

{
  "items": [
    {
      "id": "project_001",
      "name": "Agentic SDLC"
    }
  ]
}
```

The test must verify that the UI correctly handles the response.

---

# 10. E2E Testing

End-to-end tests must validate complete user workflows.

Recommended tool:

```text
Playwright
```

Critical workflows should include:

```text
Login
    ↓
Dashboard
    ↓
Create Project
    ↓
Submit Requirements
    ↓
View Agent Status
    ↓
Review Generated Output
```

Other important workflows:

* User registration
* Login/logout
* Project creation
* Project deletion
* File upload
* API interaction
* Deployment approval
* Error recovery

---

# 11. User Flow Testing

Tests must represent real user actions.

Preferred:

```text
Open application
    ↓
Click "Create Project"
    ↓
Enter project name
    ↓
Submit form
    ↓
Verify project appears
```

Avoid tests that depend heavily on internal implementation details such as:

```text
expect(component.state.foo).toBe(...)
```

Prefer:

```text
expect(screen.getByText("Project created")).toBeVisible();
```

---

# 12. Authentication Testing

Authentication tests must verify:

* Login success
* Invalid credentials
* Logout
* Session expiration
* Token expiration
* Unauthorized access
* Protected routes
* Authentication persistence

Example:

```text
Unauthenticated User
        ↓
Protected Route
        ↓
Redirect to Login
```

Test that protected pages cannot be accessed without authentication.

---

# 13. Authorization Testing

Authorization tests must verify role-based behavior.

Example:

```text
Admin
 ├── Create Project
 ├── Delete Project
 └── Deploy

Developer
 ├── Create Project
 └── View Project

Viewer
 └── View Project
```

Tests must verify that unauthorized UI actions are hidden or disabled.

Backend authorization must still be enforced independently.

---

# 14. Form Validation Testing

Every important form must test:

* Required fields
* Invalid values
* Minimum length
* Maximum length
* Invalid email
* Invalid formats
* Duplicate values
* Submission success
* Submission failure

Example:

```text
Email = invalid-email
        ↓
Validation
        ↓
Display error
        ↓
Do not submit API request
```

---

# 15. Loading States

Every API-driven component must have appropriate loading behavior.

Test:

```text
API Request
    ↓
Loading UI
    ↓
API Response
    ↓
Content UI
```

Examples:

* Spinner
* Skeleton
* Disabled submit button
* Loading text

Tests must verify that duplicate requests cannot be accidentally triggered by repeated user actions where applicable.

---

# 16. Error States

Tests must cover:

* HTTP 400
* HTTP 401
* HTTP 403
* HTTP 404
* HTTP 409
* HTTP 422
* HTTP 500
* Network failure
* Timeout

Example:

```text
API Failure
    ↓
Error Handler
    ↓
User-Friendly Message
    ↓
Retry Option
```

Do not expose stack traces or internal backend details to users.

---

# 17. Empty States

Empty states must be tested.

Example:

```text
No Projects Found

Create your first project.
```

Test that the correct empty-state UI appears when the API returns:

```json

  "items": []
}
```

---

* Submit buttons

* Colors
* Buttons

```text

      ↓
```

# 22. Accessibility Testing

Tests must validate basic accessibility requirements.

Verify:

* Semantic HTML
* Keyboard navigation
* Labels
* Accessible names
* Focus management
* Color contrast
* ARIA usage where required
* Screen-reader compatibility

Example:

```text
Input
 ↓
<label>
 ↓
Accessible name
```

Buttons must have meaningful accessible names.

Avoid:

```html
<button>
  <span>...</span>
</button>
```

when the button has no accessible name.

---

# 23. Performance Testing

Frontend tests should monitor important performance characteristics.

Verify:

* Initial page load
* JavaScript bundle size
* Large list rendering
* Image loading
* API request count
* Unnecessary re-renders

For large datasets:

```text
10,000 records
      ↓
Pagination / Virtualization
      ↓
Render visible records
```

Do not render unnecessarily large datasets directly into the DOM.

---

# 24. Security Testing

Frontend security tests must verify:

* XSS prevention
* Unsafe HTML handling
* Secure authentication behavior
* Protected routes
* Sensitive data exposure
* Token handling
* Secure API usage
* File upload validation
* URL validation

Never place:

```text
API keys
AWS credentials
Database passwords
Private tokens
```

inside frontend source code.

---

# 25. Browser Compatibility

Critical workflows should be tested on supported browsers.

Recommended:

```text
Chromium
Firefox
WebKit
```

At minimum, critical user workflows must work consistently across supported browsers.

---

# 26. Test Data and Fixtures

Reusable test data must be stored as fixtures.

Example:

```text
tests/
└── fixtures/
    ├── users.ts
    ├── projects.ts
    └── agents.ts
```

Example:

```typescript
export const testUser = {
  email: "test@example.com",
  role: "developer"
};
```

Do not use real production user data.

---

# 27. Mocking Standards

Mock only external dependencies when necessary.

Good candidates:

* APIs
* Authentication providers
* External services
* Browser APIs
* Time
* Random values

Avoid excessive mocking of internal application behavior.

The objective is to test realistic application behavior.

---

# 28. Test Coverage Standards

Coverage must focus on meaningful functionality rather than achieving an arbitrary percentage.

Recommended minimum target:

```text
Critical business logic      ≥ 90%
Reusable components          ≥ 80%
Utility functions            ≥ 90%
Overall frontend             ≥ 80%
Critical user workflows      100%
```

Coverage percentage alone must not be considered proof of application quality.

---

Frontend tests must run automatically in CI/CD.


# 30. Failure Handling

When a test fails, the Testing Agent must identify:

```text
Test Name
    ↓
Failure Reason
    ↓
Affected Component
    ↓
Expected Result
    ↓
Actual Result
    ↓
Suggested Fix
```

Example:

```text
Test:
Create Project

Expected:
Project appears in project list

Actual:
Project list remains empty

Possible Cause:
API response not updating frontend state
```

# 40. Agentic SDLC Frontend Testing Rule

The Testing Agent must never consider a frontend implementation complete merely because the application builds successfully.

A frontend implementation is considered valid only when:

```text
Build
  +
Unit Tests
  +
Component Tests
  +
Integration Tests
  +
Critical E2E Tests
  +
Accessibility
  +
Responsive Validation
  +
Figma Compliance
  +
Security Validation
```

meet the project's defined acceptance criteria.

**Final Rule:**

> The Testing Agent must validate the frontend from the user's perspective, verify critical workflows, compare the implementation against the approved Figma design, identify failures, and block downstream deployment when critical tests fail.


# 28A. Severity-Based Pass Criteria

Frontend test results must be classified according to severity.

| Severity     | Description                                                                                                                   | Pass Criteria                                  | Deployment Impact               |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ------------------------------- |
| **Critical** | Core functionality completely broken, security issue, authentication failure, data loss, deployment-blocking workflow failure | **0 Critical failures allowed**                | **Block deployment**            |
| **High**     | Major business functionality broken or important user workflow fails                                                          | **0 High failures allowed** for production     | **Block production deployment** |
| **Medium**   | Non-critical functionality partially broken or significant UI/UX issue                                                        | Limited failures may be accepted with approval | May proceed with approval       |
| **Low**      | Minor UI issue, cosmetic defect, non-critical edge case                                                                       | May be accepted                                | Does not block deployment       |

## Pass Rules

The Testing Agent must apply the following rules:

```text
Critical failures > 0
        ↓
FAIL
        ↓
Block deployment
```

```text
High failures > 0
        ↓
FAIL for Production
        ↓
Fix + Retest
```

```text
Only Medium / Low failures
        ↓
Review
        ↓
Approval if acceptable
        ↓
May PASS
```

### Automatic PASS

A frontend release can be marked **PASS** when:

```text
Critical failures = 0
        AND
Production-blocking High failures = 0
        AND
Critical workflows = PASS
        AND
Build = PASS
        AND
Required security checks = PASS
```

### Automatic FAIL

The Testing Agent must return:

```json
{
  "status": "failed",
  "deployment_allowed": false,
  "reason": "Critical or production-blocking High severity failures detected"
}
```

when any deployment-blocking failure exists.

### Severity-Based Testing Agent Decision

```text
Test Execution
      ↓
Classify Failures
      ↓
Critical?
 ┌────┴────┐
Yes       No
 ↓         ↓
FAIL      High?
Block    ┌───┴───┐
         Yes     No
          ↓       ↓
        FAIL    Medium/Low
        Prod       ↓
        Review → Approval
                    ↓
                   PASS
```

The Testing Agent must never mark a release as **PASS** merely because the overall test pass percentage is high. Severity and business impact take priority over raw test count.

**Final Severity Rule:**

> Zero Critical failures are mandatory. Production-blocking High failures are not allowed. Medium and Low failures may be accepted only when they do not violate project acceptance criteria and the appropriate approval is obtained.
