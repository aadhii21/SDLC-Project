# Python Development Standards

## 1. Purpose

This document defines the Python development standards for all backend applications generated by the Agentic SDLC platform.

The Backend Agent must follow these standards when generating, reviewing, testing, and modifying Python code.

---

# 2. Python Version Standards

Use a currently supported Python version.

Recommended:

```text
Python 3.12+
```

The exact version must be defined in the project configuration.

Example:

```text
requires-python = ">=3.12,<4.0"
```

Do not use deprecated Python features when a supported alternative exists.

---

# 3. Code Quality Principles

Python code must be:

* Readable
* Maintainable
* Testable
* Modular
* Type-safe
* Secure
* Reusable
* Production-ready

Prefer simple code over unnecessary abstraction.

Avoid:

```python
def process(data, mode, flag=True, option=None, config=None):
    ...
```

when smaller, focused functions can be used.

---

# 5. Naming Standards

Use `snake_case` for:

* Variables
* Functions
* Methods
* Modules

Example:

```python
project_id = "project_001"

def create_project():
    ...
```

Use `PascalCase` for classes:

```python
class ProjectService:
    ...
```

Use `UPPER_SNAKE_CASE` for constants:

```python
MAX_RETRY_COUNT = 3
```

Avoid unclear names:

```python
x
data
temp
foo
bar
```

unless the scope is trivial.

---

# 6. Functions

Functions should have one clear responsibility.

Good:

```python
def validate_project_name(name: str) -> bool:
    return len(name.strip()) > 0
```

Avoid large functions containing:

```text
Validation
+
Database operations
+
API calls
+
Business logic
+
Logging
```

Break them into smaller functions.

---

# 7. Type Hints

Type hints are mandatory for production Python code.

Example:

```python
def get_project(project_id: str) -> Project:
    ...
```

For collections:

```python
def get_project_ids() -> list[str]:
    ...
```

Use `Optional` or modern union syntax where appropriate:

```python
def get_project(project_id: str) -> Project | None:
    ...
```

Avoid untyped public functions.

---

# 8. Pydantic Standards

Use Pydantic models for structured external input and output.

Example:

```python
from pydantic import BaseModel


class ProjectCreate(BaseModel):
    name: str
    description: str | None = None
```

Validate:

* Required fields
* Field formats
* Length
* Allowed values
* Business constraints

Do not blindly trust incoming data.

---

# 9. Configuration Management

Configuration must not be hardcoded.

Bad:

```python
DATABASE_URL = "postgresql://admin:password@localhost/db"
```

Good:

```python
from pydantic_settings import BaseSettings


class Settings(BaseSettings):
    database_url: str
    environment: str = "development"
```

Use environment variables or a secure configuration system.

Never commit:

```text
Passwords
API keys
AWS credentials
Private keys
JWT secrets
Database credentials
```

---

# 10. Exception Handling

Do not silently ignore exceptions.

Bad:

```python
try:
    process()
except Exception:
    pass
```

Good:

```python
try:
    process()
except ValueError as exc:
    logger.warning("Invalid project data: %s", exc)
    raise
```

Catch specific exceptions whenever possible.

---

# 11. Custom Exceptions

Business-specific errors should use custom exceptions.

Example:

```python
class ProjectNotFoundError(Exception):
    pass
```

Service layer:

```python
raise ProjectNotFoundError(project_id)
```

API layer can then convert the exception into an appropriate HTTP response.

---

# 12. Logging

Use Python's logging framework.

Example:

```python
import logging

logger = logging.getLogger(__name__)

logger.info("Project created: %s", project_id)
```

Never log:

```text
Passwords
Access tokens
API keys
Authorization headers
Private credentials
Sensitive user data
```

Use structured logging where supported.

---

# 13. Database Access

Database operations must be separated from business logic.

Recommended:

```text
Route
 ↓
Service
 ↓
Repository
 ↓
Database
```

Example:

```python
class ProjectRepository:

    async def get_by_id(
        self,
        project_id: str
    ) -> Project | None:
        ...
```

Do not put complex database queries directly inside API routes.

---

# 14. SQL Injection Prevention

Never construct SQL queries using string concatenation.

Bad:

```python
query = f"SELECT * FROM users WHERE id = '{user_id}'"
```

Use parameterized queries or ORM mechanisms.

---

# 15. Async Standards

Use asynchronous programming for I/O-bound operations where the framework and libraries support it.

Example:

```python
async def get_project(project_id: str):
    project = await repository.get_by_id(project_id)
    return project
```

Do not perform blocking operations inside async endpoints.

---

# 16. HTTP Client Standards

External API calls must use a proper HTTP client.

Example:

```python
import httpx


async with httpx.AsyncClient() as client:
    response = await client.get(url)
```

External calls must have:

* Timeout
* Error handling
* Retry strategy where appropriate
* Logging
* Response validation

Never make unlimited external requests.

---

# 17. Dependency Management

Dependencies must be explicitly declared.

Example:

```text
fastapi
uvicorn
pydantic
sqlalchemy
alembic
httpx
```

Pin or constrain versions according to the project's dependency policy.

Unused dependencies must be removed.

---

# 18. Virtual Environment

Local development must use an isolated environment.

Example:

```bash
python -m venv .venv
```

Activate it before installing dependencies.

Do not commit:

```text
.venv/
```

to Git.

---

# 19. Formatting

Use an automated formatter.

Recommended:

```text
Ruff
```

Formatting must be consistent across the project.

The Backend Agent should format generated Python code before finalizing it.

---

# 20. Linting

Use automated linting.

Recommended:

```text
Ruff
```

The CI/CD pipeline must fail when configured blocking lint errors are detected.

---

# 21. Static Type Checking

Use static type checking for important backend applications.

Recommended:

```text
mypy
```

or an equivalent project-approved type checker.

Example:

```bash
mypy app/
```

Type-checking failures must be reviewed before deployment.

---

# 22. Testing

Python applications must have automated tests.

Recommended:

```text
pytest
```

Testing layers:

```text
Unit Tests
    ↓
Integration Tests
    ↓
API Tests
    ↓
E2E Tests
```

Critical business logic must have strong test coverage.

---

# 23. Test Naming

Use descriptive test names.

Good:

```python
def test_create_project_returns_created_project():
    ...
```

```python
def test_create_project_rejects_empty_name():
    ...
```

Avoid:

```python
def test_1():
    ...
```

---

# 24. Dependency Injection

Use dependency injection for replaceable dependencies.

Examples:

* Database sessions
* Authentication
* External APIs
* Repositories
* Services

Example:

```python
def get_project_service() -> ProjectService:
    return ProjectService(...)
```

This makes code easier to test.

---

# 25. API Layer Separation

FastAPI routes should remain thin.

Preferred:

```python
@router.post("/projects")
async def create_project(
    request: ProjectCreate,
    service: ProjectService = Depends(get_project_service),
):
    return await service.create_project(request)
```

Avoid putting extensive business logic inside the route.

---

# 26. Service Layer

Business logic should primarily live inside services.

Example:

```python
class ProjectService:

    async def create_project(
        self,
        request: ProjectCreate,
    ) -> Project:
        ...
```

Services may coordinate:

```text
Repository
External API
Validation
Business Rules
Events
```

---

# 27. Repository Layer

Repositories should handle data persistence.

Example:

```python
class ProjectRepository:

    async def create(self, project: Project) -> Project:
        ...

    async def get_by_id(
        self,
        project_id: str,
    ) -> Project | None:
        ...
```

The repository should not contain unrelated business logic.

---

# 28. Security Standards

Python applications must follow the project's security standards.

Mandatory protections include:

```text
Input Validation
Authentication
Authorization
Secret Management
Dependency Security
Safe Error Handling
Secure Logging
SQL Injection Prevention
Command Injection Prevention
Path Traversal Prevention
```

Never execute arbitrary user input.

---

# 29. File Handling

Uploaded files must be validated.

Validate:

* File size
* File type
* File extension
* Content where appropriate
* Filename

Never directly trust:

```python
filename = user_input
```

when constructing filesystem paths.

Use safe path handling.

---

# 30. Command Execution

Avoid shell execution unless explicitly required.

Never directly execute user-provided commands.

Bad:

```python
import os

os.system(user_command)
```

For Agentic SDLC code execution, execution must occur inside the approved sandbox architecture.

---

```text
Agent
 ↓
Reasoning
 ↓
Tool Selection
 ↓
Tool Execution
 ↓

 ↓
Result
```

Agents must not directly access arbitrary system resources.

Tool calls must be:

* Validated

# 32. LLM Integration

LLM calls must be isolated behind service or client abstractions.

Example:

```python
class LLMService:

    async def generate(
        self,
        prompt: str,
    ) -> str:
        ...
```

Do not scatter provider-specific LLM calls throughout the application.

This allows providers to be changed without rewriting the entire application.

---

# 33. RAG Integration

RAG functionality should follow:

```text
Query
 ↓
Embedding
 ↓
Vector Search
 ↓
Filtering
 ↓
Retrieved Context
 ↓
LLM
 ↓
Response
```

Retrieved content must be treated as untrusted data.

The application must not blindly execute instructions retrieved from documents.

---

# 34. Agent State

Long-running agents must use structured state.

Example:

```python
class AgentState(TypedDict):
    project_id: str
    requirements: str
    design_status: str
    frontend_status: str
    backend_status: str
    testing_status: str
```

Avoid storing arbitrary unstructured state when structured state is possible.

---

# 35. Retry Standards

Retries should only be used for transient failures.

Examples:

```text
Network timeout
Temporary service unavailable
Rate limiting
Transient AWS failure
```

Do not endlessly retry deterministic failures.

Use:

```text
Maximum Retry Count
+
Backoff
+
Failure Logging
```

Example:

```text
Attempt 1
   ↓
Wait
   ↓
Attempt 2
   ↓
Wait
   ↓
Attempt 3
   ↓
Fail
```

---

# 36. Timeouts

All external network operations must have explicit timeouts.

Example:

```python
async with httpx.AsyncClient(timeout=30.0) as client:
    ...
```

Never allow external calls to wait indefinitely.

---

# 37. Idempotency

Operations that may be retried must be designed for idempotency where appropriate.

Examples:

```text
Create Deployment
Update Project
Trigger CI/CD
Create Infrastructure
```

Use idempotency keys or state checks when necessary.

---

# 38. Concurrency

Concurrency must be handled carefully.

Consider:

* Race conditions
* Duplicate jobs
* Database locking
* Shared state
* Concurrent agent execution

For long-running Agentic SDLC jobs:

```text
Job ID
 ↓
Job State
 ↓
Worker
 ↓
Checkpoint
 ↓
Resume
```

---

# 39. Background Jobs

Long-running operations must not block API requests.

Examples:

```text
Code generation
RAG ingestion
Docker build
Testing
Terraform deployment
Agent workflow
```

Use background workers or a task queue where required.

---

# 40. API Response Models

FastAPI endpoints should define response schemas.

Example:

```python
@router.get(
    "/projects/{project_id}",
    response_model=ProjectResponse,
)
async def get_project(project_id: str):
    ...
```

Responses must have predictable structures.

---

# 41. Pagination

Endpoints returning potentially large collections must use pagination.

Example:

```text
GET /api/v1/projects?page=1&page_size=20
```

or cursor-based pagination when appropriate.

Do not return unlimited database records.

---

# 42. API Error Responses

Errors should follow a consistent structure.

Example:

```json
{
  "error": {
    "code": "PROJECT_NOT_FOUND",
    "message": "Project was not found",
    "request_id": "req_123"
  }
}
```

Do not expose internal stack traces.

---

# 43. Request IDs

Requests should have a traceable request ID.

Example:

```text
Client
 ↓
Request ID
 ↓
FastAPI
 ↓
Service
 ↓
Database
 ↓
External Service
```

The same request ID should be included in relevant logs.

---

# 44. Documentation

Public APIs must have documentation.

FastAPI's OpenAPI documentation should accurately represent:

* Endpoints
* Request models
* Response models
* Authentication
* Errors
* Parameters

Do not leave generated API documentation inconsistent with implementation.

---

# 45. Environment Separation

Python applications must support separate environments.

```text
development
staging
production
```

Configuration must not be mixed between environments.

Production credentials must never be used in development or tests.

---

# 46. Database Migrations

Database schema changes must use migrations.

Recommended:

```text
Alembic
```

Do not manually modify production database schemas without an approved migration process.
