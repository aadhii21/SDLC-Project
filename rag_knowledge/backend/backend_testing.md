# Backend Testing Standards

## 1. Purpose

This document defines the testing standards for backend applications generated by the Agentic SDLC platform.

The Backend Agent and Testing Agent must follow these standards when generating, executing, reviewing, and validating backend tests.

---

# 2. Testing Standards Summary

Backend applications must be:

```text
Testable
+
Reliable
+
Secure
+
Maintainable
+
Production-Ready
```

Testing must cover:

```text
Unit Tests
    ↓
Integration Tests
    ↓
API Tests
    ↓
E2E Tests
    ↓
Security Tests
```

The Testing Agent must validate both expected behavior and failure scenarios.

---

# 3. Testing Principles

Tests must be:

* Deterministic
* Repeatable
* Isolated
* Readable
* Maintainable
* Fast where possible
* Independent
* Meaningful

Avoid tests that depend on:

```text
Execution Order
Local Environment
Real Credentials
Uncontrolled External Services
Unstable Timing
```

---

# 4. Testing Pyramid

Follow the testing pyramid:

```text
           E2E Tests
          /---------\
       API / Integration
      /---------------\
          Unit Tests
     /-------------------\
```

Prefer a larger number of fast unit tests and fewer expensive E2E tests.

---

# 5. Test Project Structure

Recommended:

```text
tests/
│
├── unit/
│   ├── services/
│   ├── repositories/
│   └── utils/
│
├── integration/
│   ├── database/
│   └── external_services/
│
├── api/
│   ├── test_projects.py
│   ├── test_users.py
│   └── test_jobs.py
│
├── e2e/
│
├── security/
│
├── conftest.py
└── fixtures/
```

Organize tests according to application behavior and test type.

---

# 6. Unit Testing

Unit tests must validate individual units of business logic in isolation.

Examples:

```text
Service Functions
Validation Functions
Utility Functions
Business Rules
Transformations
```

Example:

```python
def test_validate_project_name_accepts_valid_name():
    assert validate_project_name("Project A") is True
```

Unit tests should avoid unnecessary database or network dependencies.

---

# 7. Service Layer Testing

Service-layer tests must validate business logic.

Example:

```python
async def test_create_project(service):
    project = await service.create_project(
        ProjectCreate(name="Test Project")
    )

    assert project.name == "Test Project"
```

Test:

```text
Success
Validation
Business Rules
Not Found
Conflict
Dependency Failures
```

---

# 8. Repository Testing

Repository tests must verify persistence behavior.

Test:

```text
Create
Read
Update
Delete
Filtering
Pagination
Transactions
Constraints
```

Database integration tests should use an isolated test database or controlled database environment.

---

# 9. API Testing

FastAPI endpoints must be tested through HTTP-level tests.

Example:

```python
def test_create_project(client):
    response = client.post(
        "/api/v1/projects",
        json={"name": "Test Project"},
    )

    assert response.status_code == 201
```

Validate both:

```text
HTTP Status Code
+
Response Body
```

---

# 10. Request Validation Testing

Test invalid requests.

Examples:

```text
Missing Required Field
Invalid Data Type
Invalid Format
Empty Value
Value Too Long
Value Too Small
Invalid Enum
Malformed Request
```

Example:

```python
def test_create_project_rejects_empty_name(client):
    response = client.post(
        "/api/v1/projects",
        json={"name": ""},
    )

    assert response.status_code == 422
```

---

# 11. Response Validation Testing

Verify that API responses follow the defined response schema.

Test:

```text
Required Fields
Data Types
Nested Objects
Nullable Fields
Sensitive Field Exclusion
Pagination Structure
Error Structure
```

Do not expose internal database fields unintentionally.

---

# 12. HTTP Status Code Testing

Verify appropriate status codes.

Examples:

```text
200 → Successful retrieval/update
201 → Resource created
202 → Accepted asynchronous operation
204 → Successful operation without response body
400 → Invalid request
401 → Unauthenticated
403 → Unauthorized
404 → Resource not found
409 → Conflict
422 → Validation failure
429 → Rate limit exceeded
500 → Unexpected server error
```

---

# 13. Authentication Testing

Protected endpoints must be tested with:

```text
Valid Credentials
Missing Credentials
Invalid Credentials
Expired Credentials
Malformed Credentials
```

Example:

```python
def test_protected_endpoint_requires_auth(client):
    response = client.get("/api/v1/projects")

    assert response.status_code == 401
```

---

# 14. Authorization Testing

Test access control separately from authentication.

Example:

```text
Admin
 ↓
Allowed

Developer
 ↓
Allowed for permitted resources

Viewer
 ↓
Read-only

Unauthorized Role
 ↓
403 Forbidden
```

Always test both allowed and denied operations.

---

# 15. Database Integration Testing

Integration tests must validate the interaction between:

```text
API
 ↓
Service
 ↓
Repository
 ↓
Database
```

Test:

```text
CRUD Operations
Transactions
Constraints
Relationships
Migrations
Rollback Behavior
```

Tests must not depend on production data.

---

# 16. External Service Testing

External APIs should normally be mocked or stubbed during automated tests.

Examples:

```text
LLM Provider
GitHub
AWS
Payment Provider
Email Service
Third-Party APIs
```

Test:

```text
Success
Timeout
Rate Limit
Authentication Failure
Invalid Response
Service Unavailable
Network Failure
```

Do not make uncontrolled external API calls during normal CI tests.

---

# 17. Mocking Standards

Mocks should be used only where they improve isolation.

Good candidates:

```text
External APIs
LLM Providers
Cloud Services
Email Services
Payment Systems
Slow Dependencies
```

Do not mock the behavior being directly tested.

Mocks must reflect realistic interfaces.

---

# 18. FastAPI Dependency Overrides

Use dependency overrides for isolated API tests.

Example:

```python
app.dependency_overrides[
    get_project_service
] = get_test_project_service
```

This allows tests to replace production dependencies without modifying application code.

---

# 19. Fixtures

Use pytest fixtures for reusable test setup.

Example:

```python
@pytest.fixture
def project():
    return Project(
        name="Test Project"
    )
```

Common fixtures:

```text
Test Client
Database Session
Authenticated User
Test Project
Mock Service
Mock External API
Test Configuration
```

Avoid excessive fixture complexity.

---

# 20. Test Data Standards

Test data must be:

* Predictable
* Minimal
* Isolated
* Reusable where appropriate
* Free from real secrets

Do not use:

```text
Production Credentials
Production Personal Data
Real API Keys
Real Payment Information
```

Generate unique identifiers where parallel execution requires them.

---

# 21. Positive and Negative Testing

Every important feature must include both:

```text
Positive Tests
+
Negative Tests
```

Positive:

```text
Valid input
Valid authentication
Expected dependency behavior
```

Negative:

```text
Invalid input
Missing data
Unauthorized access
Dependency failure
Database failure
Timeout
```

---

# 22. Boundary Testing

Test important boundaries.

Examples:

```text
Minimum Value
Maximum Value
Empty String
Maximum String Length
Zero
Negative Values
Large Values
Maximum Page Size
```

Boundary tests are especially important for validation-heavy APIs.

---

# 23. Error Handling Tests

Verify that failures produce:

```text
Correct Status Code
Correct Error Code
Safe Error Message
Request ID
No Sensitive Information
```

Example:

```json
{
  "error": {
    "code": "PROJECT_NOT_FOUND",
    "message": "Project was not found",
    "request_id": "req_123"
  }
}
```

Never expose stack traces in production-style API responses.

---

# 24. Exception Testing

Test custom business exceptions.

Example:

```python
async def test_get_project_raises_not_found(service):
    with pytest.raises(ProjectNotFoundError):
        await service.get_project("invalid-id")
```

Also verify that API exception handlers convert exceptions into the correct HTTP responses.

---

# 25. Async Testing

Asynchronous code must be tested using appropriate async testing support.

Example:

```python
@pytest.mark.asyncio
async def test_get_project():
    result = await service.get_project("project_123")

    assert result is not None
```

Do not introduce blocking operations into async test paths unnecessarily.

---

# 26. Background Job Testing

Long-running jobs must be tested independently from the HTTP request lifecycle.

Test:

```text
Job Creation
Job Queuing
Job Execution
Job Status
Job Completion
Job Failure
Job Retry
Job Cancellation
```

Example:

```text
POST /api/v1/jobs
        ↓
202 Accepted
        ↓
job_id
        ↓
GET /api/v1/jobs/{job_id}
        ↓
queued → running → completed
```

# 30. Security Testing

Backend tests must validate important security controls.

Test:

```text
Authentication
Authorization
Input Validation
SQL Injection Prevention
Command Injection Prevention
Path Traversal Prevention
File Upload Validation
Rate Limiting
Secret Exposure
Sensitive Data Exposure
```

Security failures must be treated as blocking according to project severity policy.

---

# 31. API Contract Testing

API tests must verify that implementation matches the approved API design.

Validate:

```text
HTTP Method
Endpoint
Parameters
Request Schema
Response Schema
Status Codes
Error Schema
Authentication
```

Breaking API contract changes must fail validation.

---

# 32. Database Migration Testing

Database migrations must be tested.

Validate:

```text
Migration Applies Successfully
Migration Is Reversible Where Required
Schema Matches Models
Constraints Are Correct
Existing Data Is Preserved
```

Migration failures must block deployment.

---

# 33. Idempotency Testing

Retryable operations must be tested for duplicate execution.

Example:

```text
Request 1
    ↓
Create Deployment

Request 2
    ↓
Same Idempotency Key

Expected:
    ↓
No Duplicate Deployment
```

Test repeated requests and concurrent requests where applicable.

---

# 34. Concurrency Testing

Test operations that may execute concurrently.

Examples:

```text
Two Users Updating Same Resource
Duplicate Job Submission
Concurrent Agent Execution
Database Race Conditions
Multiple Workers
```

Verify that the final state remains consistent.

---

# 35. Pagination Testing

Test:

```text
First Page

Last Page
Empty Page
Invalid Page
Maximum Page Size
```

Also verify:

```text
Total Count
Page Size
Next/Previous Cursor
Ordering
```

when those fields are part of the API contract.

---

# 36. File Upload Testing

Test:

```text
Valid File
Invalid Extension
Invalid MIME Type
Oversized File
Empty File
Malicious Filename
Path Traversal Attempt
Malformed Content
```

Uploaded content must never be trusted automatically.

# 37. Health Check Testing

Verify:

```text
/health
/readiness
```

Expected behavior should be defined for:

```text
Application Available
Database Available
Required Dependency Unavailable
```

Health endpoints must not expose sensitive infrastructure information.

---

# 38. Performance Testing

Performance tests should be added for important or high-traffic APIs.

Measure:

```text
Response Time
Throughput
Concurrent Requests
Database Performance
External API Latency
Resource Usage
```

Define performance thresholds for critical endpoints.

---

# 39. Test Isolation

Tests must not depend on each other's execution.

Each test should control its own:

```text
Data
State
Mocks
Environment
Authentication
```

Clean up temporary resources after tests.

---

# 40. Test Naming Standards

Use descriptive names.

Good:

```python
def test_create_project_returns_201_for_valid_request():
    ...
```

```python
def test_create_project_returns_422_for_empty_name():
    ...
```

```python
def test_admin_can_trigger_production_deployment():
    ...
```

Avoid:

```python
def test_1():
    ...
```

---

# 41. Test Coverage

Coverage should measure meaningful tested behavior rather than only a percentage.

Focus on:

```text
Critical Business Logic
Authentication
Authorization
Security Controls
Error Handling
Agent Workflows
Important API Paths
```

Coverage thresholds should be defined by project requirements.

Do not write meaningless tests only to increase coverage.

# 43. CI/CD Testing Standards

The CI/CD pipeline must automatically execute required tests.

A blocking test failure must:

```text
Fail Pipeline
     ↓
Prevent Artifact Promotion
     ↓
Prevent Deployment
```

unless an explicitly approved exception exists.

---

# 44. Severity-Based Pass Criteria

Test failures should be classified by severity.

| Severity | Criteria                                                     | Pipeline Result            |
| -------- | ------------------------------------------------------------ | -------------------------- |
| Critical | Security breach, data corruption, production-blocking defect | Fail                       |
| High     | Major functionality or API contract failure                  | Fail                       |
| Medium   | Important but non-blocking defect                            | Review / approval required |
| Low      | Minor defect with limited impact                             | May pass                   |

Default rule:

```text
Critical = 0 allowed
High = 0 allowed
Medium = Allowed only with approval
Low = May be accepted
```

---

# 45. Test Failure Handling

When a test fails, the Testing Agent should determine:

```text
Failure Type
    ↓
Root Cause
    ↓
Severity
    ↓
Affected Component
    ↓
Recommended Fix
```

Do not simply report:

```text
TEST FAILED
```

Provide actionable failure information.

---

# 46. Flaky Test Handling

Flaky tests must be identified and fixed.

Common causes:

```text
Timing Dependency
Race Condition
External Service
Shared State
Random Data
Environment Dependency
```

Do not permanently hide flaky tests by disabling them.

Retries may be used temporarily for diagnosis but must not replace fixing the underlying problem.

# 52. Final Backend Testing Rule

The Testing Agent must not consider a backend complete merely because the application starts successfully.

The backend must be validated through:

```text
Functional Testing
+
Integration Testing
+
API Testing
+
Security Testing
+
Agentic AI Testing
+
Quality Gates
```

**Final Rule:**

> A backend can be handed to deployment only when all Critical and High severity failures are resolved, required tests pass, security validation passes, API contracts are satisfied, and the generated test report confirms the backend meets the project's quality standards.
